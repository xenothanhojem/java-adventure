4.1  Introduction to Computational Thinking 
We use computers to help us solve problems, but before we can go about solving the problem, we 
need to understand the problem and have a method that we can use to produce a solution. 
Computational thinking provides us with this method by taking a complex problem and using four key 
techniques in the problem-solving process. 
The four techniques to computational thinking: 
• decomposition – dividing a complex problem or system into smaller, more manageable parts 
• pattern recognition – looking for similarities between and within each part 
• abstraction – focusing on the important information only, ignoring irrelevant detail and 
focussing on solving each part in turn so that the combined parts solve the problem 
• algorithms - developing a step-by-step solution to the problem, or the rules to follow to solve 
the problem

Each of these techniques are vitally important in the process of problem solving. Computational 
Thinking is not limited to programming or Computer Science, it can be used to solve problems in any 
subject area like English, History, Mathematics and Science.

Computational thinking involves analysing a complex problem and breaking it down into smaller, more 
manageable parts (decomposition). Each of these smaller parts are sub-problems in themselves 
that again can be analysed. These smaller problems may have existing solutions (pattern

each of the smaller problems can be designed (algorithms).

Each of these stages work together when solving a problem. You may read a problem and ignore 
some irrelevant detail (abstraction), then decompose the problem into parts, some parts may need to 
be further decomposed. You may find one part is similar to previous code (pattern recognition) and 
two parts are also similar in nature (again pattern recognition). To write an algorithm for each part you 
will focus on each part (abstraction), test each part and then combine the parts to form the solution.

4.2.1 Understanding the Problem 
The problem may not be clearly defined and may be stated by someone who is unfamiliar with 
computers in a vague and ambiguous manner. There may be information that is not relevant to the 
solution like the type of computer they are using, or the day of the week they use the program. As a 
programmer, you need to make sure that you are solving the problem that the user intended. 
Otherwise a lot of time and effort will be wasted. 
When you analyse a problem statement, do the following:  
• Read the problem carefully and make sure you understand it. 
• Underline words that describe what is to be done, such as find the average, calculate VAT. 
• State in your own words what you need to do. 
• List all the facts that are given about the problem.

4.3 Pattern Recognition 
Before you code a solution to a problem or subproblem you find that the problem is similar to others: 
1. there may be an existing program that can be used to solve the problem. This is always the 
first option. If the code exists, it has been tested and is probably error free.  
2. there may be pre-written methods that can be called to completely or partially solve the 
problem. Before we write more code, try to look for a method that may be useful in solving the 
problem. Java has many prewritten classes that are reliable. For example, we do not need to 
write code to manipulate and validate dates as Java has many classes to do this. 
3. there may be existing generic algorithms that can be adapted to solve the problem. If we can 
model the problem on a similar problem, we will have some idea how to solve the new problem. 
This year we will learn generic algorithms such as swopping variables, finding the highest, 
lowest, the sum and average of a set of numbers. Sometimes these algorithms can be slightly 
adapted to solve similar type problems.  
4. some of the code may need to be repeated. Later on, you will learn how to use loops to repeat 
programming statements.

4.4 Abstraction 
Abstraction is a useful tool and its main purpose is to focus on what is important to the problem and 
ignore the rest. It can be used for the main problem, or for each part of the problem. For the main 
problem, a programmer needs to determine what information do they need, and what can they ignore. 
For example, if a problem requires a simple calculation to be done, then the day the calculation is 
done, the person doing the calculation and the type of pen they used are not important to solving this 
problem. 
Most problems are very complex and one way to manage this complexity is to break the problem into 
parts (decomposition) and then focus on each task individually. Focussing on each task can be 
thought of zoom in – zoom out. Think of a camera that zooms in to a picture. It can only see what is 
in the view finder. It eliminates everything else. Abstraction is also the zooming in on one task, 
ignoring other tasks. It is used repeatedly in problem solving. Initially, we abstract the relevant details 
to determine the problem to solve, then we decompose the problem into tasks and again zoom into a 
task to find a solution to that task ignoring the other tasks. Once that task is solved, we zoom out and 
zoom into the next task, systematically working through each until all the tasks are solved and are 
combined to solve the main problem.

4.5 Algorithms 
An algorithm is a step by step solution to a problem. It can be either a flow chart or pseudocode. A 
flow chart is a visual representation of the steps in the solution where steps are written in a variety of 
connected shapes.  
Pseudocode is a generic fictitious language that can be converted into ANY programming language. 
Given an algorithm in pseudocode, a programmer can write the solution in their choice of language.  
4.5.1 Data Structure 
The information in the problem is stored in a data structure, which is the main variables that are used 
to store the data for input, processing and output. Some variables are used to store data right 
throughout the program and others are needed to store data temporarily. The temporary or 
intermediate variables are not considered part of the main data structure. The algorithms and the data

4.5.3 Pseudocode 
The following rules can be used to write an algorithm in pseudocode. 
• start the code with the word "begin" and finish with the word "end". Indent all instructions 
between "begin" and "end".  
• one line of pseudocode code is similar to a line of Java code 
• an assignment statement is an arrow  pointing left, not an equals = sign 
• no semi colons at the end of a statement 
• variable types vary from one language to another, so do not include any variable declarations 
• do not use any method names that only belong to one language. For example, an algorithm will 
not use bug.move() but rather say something like move bug 1 block.  
• mathematical symbols such as <,>. =, ≠, ≥ and ≤ are universal in any language and can be used 
• use the word input when entering data from the keyboard  
• use display when displaying data on the screen

4.6.1 User Friendliness 
The term "user-friendly" is used to describe programs which are well designed from the user 
interface perspective. If a program is user-friendly, it does not mean that the program is full of friendly 
greetings, but rather that it is relatively easy to use by the end user (we also say that usability is high). 
A user-friendly program should use clear prompts to tell the user exactly what data to input. It should 
also display well lined up output, in an uncluttered way, with meaningful messages, in particular error 
messages. 
A user-friendly program can help to avoid run-time errors because the user will know exactly what to 
type in. 
4.6.2 Designing a Simple User Interface 
Refer to section 7.8 of Learning Unit 7 in Exploring IT: Theory Grade 10 for the principles of User 
Interface Design. 
The user interface is how your program communicates with the user. It is important to choose the 
right method of communication. The showMessageDialog is useful for shorter messages; however, 
System.out.println provides a larger area to display data. If you have a lot of information to give the 
user, try to structure it so that it is laid out in columns or is spaced out in such a way the user can read 
the information easily. Also remember that each time the showMessageDialog is used, the user 
must click OK to close the box. If you are displaying a large amount of data with each line of data 
being displayed by separate showMessageDialog calls, the user could get frustrated having to click 
many times. Rather combine all the information into one statement and use \n to put the data on 
separate lines or use System.out.println. 
The statement

         +".\nHow are you?\nI am fine");

4.6.3 Readability     
A program is user-friendly if an end user can use it easily when it is run. A program is readable if 
another programmer can understand its code easily. The more readable a program is, the easier it is 
to find errors. 
In business, more than one person is usually involved in developing a program or a set of programs. 
Often the person who originally wrote the code for a program has left the company for which he wrote 
the code. In this case, another programmer must maintain the code by correcting errors or adding 
enhancements. It could take a long time for another programmer to understand the code if it is badly 
written and time costs money! 
At school level, there are some simple techniques that can make your program more readable.

1. Use descriptive variable names 
If a variable is going to store a sum call it sum (or total). It can be misleading when a variable 
determines the average but is called sum. 
2. Place one statement on a line 
Code is easier to read if there is only one statement on a line including brackets.  
3. Indent your code correctly 
Any code between an opening and closing curly bracket must be indented. This will be particularly 
helpful to identify errors when you use loops and selection statements later on. Your IDE may provide 
a function to indent code. 
4. Include comments 
If the variable name does not make the code easy to understand, include comments. At this stage, 
the method names are fairly explanatory, but if you are doing something new that you doubt you will 
understand later, add in some explanations in the form of comments. 
5. Separate code 
Use blank lines to separate sections of code. Try to group code that performs a similar function 
together. For example, use sections to: declare variables; perform calculations and produce output. 
Later on, we will write our own methods to break the code into sections. 
6. Follow conventions 
• By convention, identifiers in Java start with lowercase letters.     
• The identifier should reflect the contents of the variable.  
Your teacher may have other conventions that should be followed. Use them as it makes marking 
quicker for your teacher and it's easier to understand your friends' programs.

4.6.4.1 Syntax, Run time and Logical Errors 
• a syntax error is an error picked up by the compiler, such as a semi colon missing. It is the 
lowest level of errors and is the easiest to find as your IDE should give some kind of error 
message. 
• a run time error is when a program compiles but does not run, for example trying to determine 
the square root of a negative number. Run time errors are one level up from syntax errors. 
When the program unexpectedly stops, your IDE should indicate where in the code the program 
halted and give an error message. 
• logical errors occur when there is an error in the logic of a program statement or a sequence of 
statements are in the incorrect order. The program compiles and runs but does not do what you 
wanted. There is no error message making logical errors more difficult to find.  
4.7 Testing 
The problem has not been solved until it has been tested. While it is not possible to test each and 
every data value, you need to choose data that will effectively test your program. You need to predict 
what result your test data should produce and then run the program to check that you are correct.  
Try to choose test data that will expose the logical errors in your program. Testing should not be done 
by the original programmer but rather by someone who is not familiar with the program. The 
programmer who wrote the program usually has become accustomed to the way it runs and generally 
is unable to test it objectively. 
4.7.1 Standard, Extreme and Abnormal Data 
Use three types of test data, standard, extreme (boundary) and abnormal. Standard data has 
values within the allowable range, extreme data are values on the limits of the range and abnormal 
data are incorrect values. For example, if a variable can have values between 1 and 10, then 
standard data would be any value from 2 to 9. Extreme data would have values on the limits 0, 1 and 
10, 11. Values 1 and 10 would be correct extreme values but 0 and 11 would be extreme incorrect 
values. Abnormal values would be 'p', <F7> and -3.  
4.7.2 Acceptance Testing 
A program is tested for acceptance in that it satisfies all the criteria that were originally stated. If a 
program or system of programs do not meet the original criteria, then they are not acceptable. 
Consider if a client commissions a company to write a product to solve a certain problem. For 
example, to record and determine the wages of each employee paid weekly. The system that is 
designed must do exactly that. The client is involved in the acceptance test procedure and only once 
the client is fully satisfied that the system meets all their criteria, that the product is signed off and the 
client will then complete all payments.

4.7.3 Trace Tables 
A trace table is a tool that is used to work out, line by line what will happen when a program executes. 
It is also a good way of locating a logical error. Trace Tables are done on paper to work out the values 
of the variables in a program. Not only does this help to find logical errors but it also helps to 
understand the purpose of the program. 
Errors in programs are often called bugs. Long ago computers were so big that actual bugs crept into 
them and caused problems. In those days, you could debug by calling the exterminators!
